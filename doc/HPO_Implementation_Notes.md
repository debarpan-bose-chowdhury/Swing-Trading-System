# HPO — implementation notes (phases 1-5)

Built from `doc/HPO_TDD.md`. This records what was decided while reading the TDD against the repo, and where the code differs from the TDD text.

## Decisions (answered by the owner)
- Scope of the first drop: phases 1, 1b and 2 (skeleton, space, objective, pool, Sobol study with resume/progress, charts 1-10, live dashboard, sensitivity). Samplers beyond Sobol/TPE, robustness, gate, holdout, promotion and candidate charts 11-24 are later phases (their CLI commands exit 1 with a message).
- `hpo` reaches `backtest` only through `backtest/api.py`, which gained thin re-exports (`limit_threads`, `init_worker`, `perf`, `pbo_cscv`, `deflated_sharpe`, `sharpe`, `config_hash`, `deep_merge`), `base_configs()`, `registry()`, a `monitor` hook (`replay.simulate` and `evaluate_config`, default None = unchanged behaviour) and `windows(start=, required_purge=)`.
- Baseline (trial 0) = the shipped `app/config`; bounds come from the register; a bound that excludes the live value is widened to it (`minNewOrderInr` 2000..10000 -> 2000..25000). Bounds the register lacks are in `hpo/config/space_extra.json` (proposed, for review).
- Effective-N cap before a study: cumulative effective N + planned trials x observed effective/raw ratio (default 0.3 before history) must be <= cap; `--override-cap "reason"` is logged.

## Where the code differs from, or fills in, the TDD
- The register has no `stage` column; stages are assigned by group in `space_extra.json` (stage 0 = the six sizing dimensions).
- Per-bucket strategy values: base (first bucket) + offsets for the other two buckets = 36 dimensions, the TDD's "4 x 3 x 3". The space has 102 dimensions in all (93 tunable, 9 risk-limit frozen); the Stage A screen over `class:tunable` is therefore ~93 dimensions, above the TDD's "~60" and near its "beyond 80 is not defensible" line. Offsets can be excluded in the study file.
- Folds, purge and start come from the whole space (longest look-back 250), so fold boundaries never change between studies.
- f1 scores the 1-year fold windows only, while f2 covers the full pre-holdout span including the first (5-year "train") years; this follows the TDD but is an inconsistency worth revisiting.
- Trials that cannot be scored (rejected point, aborted run) carry placeholder objectives (-100% CAGR, 100% depth) and a violated constraint; they are never read as performance and are greyed in reports.
- PED-ANOVA importances are re-normalised to shares; Morris/Sobol indices are not implemented (Spearman is the cross-check).
- Charts: Plotly bundled inline; a per-chart SVG export is the Plotly toolbar button, not a file written next to the report (no server-side image engine).
- Resume refuses on a changed `code_sha` (as the TDD says), which includes any `git pull`; `study run --accept-code-change "reason"` continues the study when only the commit changed (logged in checkpoint.json; changed data, configs, windows or schema are never accepted).
- Not run here: the sandbox has no `app/data`, so engine tests use the synthetic world and real timing/Stage 0 runs happen on your PC.

## Phase 3 (samplers, constraints, front, stages)
- Samplers: `sobol` (QMC), `tpe` (multivariate, `group=True`, constant liar) and `gp` (Optuna `GPSampler`, deterministic objective). Constraints reach the samplers through `trial.set_constraint` (Optuna 5.0; no `constraints_func`); verified on a known landscape: TPE ends with 100% feasible trials in the last half against about 60% for Sobol, and GP handles two objectives plus constraints.
- `gp` needs PyTorch, an optional extra: `uv sync --project hpo --extra gp`. PyPI's default Linux/Windows wheel is the CUDA build (about 2.5 GB with its libraries); on your PC install the CPU build instead (`uv pip install torch --index-url https://download.pytorch.org/whl/cpu` inside `hpo/.venv`). The sandbox's index for that URL was blocked, so the GP test ran here with the CUDA wheel. GP suggestions slow down as trials grow (about 0.5 s per trial at 40 trials, here) and Optuna's GP has no constant liar, so with 8 workers it can propose near-duplicates: prefer `--workers 2-4` for Stage C.
- `front --name N [--select calmar|knee]` lists the feasible front and one pick (writes `front.json`). `stages plan --name sA` writes B1-B3 study files for the kept dimensions (signal / stops and sizing / regime and composition); a file with `from: <study>` gets its `fixed` values from that study's selected front trial at `study new`. `stages advise --name B3` applies the TDD's rule (hypervolume gain under 1% over 150 trials, importance on at most 25 parameters, no more than 30% categorical) and writes `C.yaml` (GP, 150 trials) when it says switch.
- Block 2 and 3 baselines are therefore "the earlier winner", not the live default; trial 0 of those blocks is that baseline.
- Not in this phase: the plateau-versus-spike selection test belongs to phase 4 (`robust.py`); here the known-optimum test is a smooth landscape with a constraint boundary. Regime-block "narrow bounds" are the register's own bounds.

## Phase 4 (plateau, statistics, gate, exploit audit, candidate report)
- `robust --name N` re-scores the first `top` trials of the feasible front (successive non-dominated layers) on 16 perturbations each (single +-1 grid step / +-10% on the most important searched parameters, plus 6 multi-parameter nudges). A finalist is robust when at least 80% of its neighbours stay within the per-metric tolerances (CAGR 20% relative or 2 pp, depth 3 pp, ulcer 25%) and **no single nudge is a cliff** (CAGR down by more than `robust.cliffPp` = 3 pp, or no run). The cliff rule is an addition to the TDD: with 16 neighbours over many parameters, a spike that is sensitive to one parameter alone passes the 80% share test, so the share rule alone cannot tell it from a plateau. Selection: highest Calmar among robust finalists, ties by ulcer; an empty robust set prints "keep defaults" and exits 0.
- `gate --candidate ID` runs about 2 + 10 + 25 + 16 simulations (candidate and default in detail; five stresses each; a 5 x 5 grid over the two most important parameters; the neighbours) and writes `candidates/<id>/{evidence.json, gate.json, series.parquet, returns.parquet, report.html}`; exit 3 when the gate is not met. The verdict (`gate.checks`) and the audit (`gate.audit`) are pure functions of the evidence file.
- Checks: feasible (>= 300 fills and the other constraints), deflated Sharpe at the cumulative effective N and at 2N (>= 0.95), PBO by CSCV over the whole trial matrix of the study (medoids when above 500 columns; <= 0.20), median fold CAGR above the floor and at least `oosIsMin` (0.5, new key) of the full-span CAGR, neighbourhood share, ranking against the default at doubled slippage and at a 100% write-off, BEAR and every stress-window drawdown within 5 pp of the default's, and SPA against the default (p <= 0.10; above it the candidate is labelled "adopt for feasibility or robustness only" and the check does not block).
- Stress runs: slippage x 2, charges x 1.3 (fees and charge amounts, not the GST rate), write-off 100%, a seeded 5% of names dropped (`api.drop_names`), the other universe mode (built lazily in the worker). **Not available:** the +1-day execution delay (the engine has no delay model); the dossier says so.
- The live default is run with `noAbort`: at Rs 1 lakh it never trades, and the abort rule would otherwise stop the baseline. A candidate therefore beats a no-trade baseline trivially; the SPA p-value is against that baseline and says little until the sizing minimums in the default are lowered.
- Exploit audit: assessed = parameters at a bound, cliffs, vanished-name write-offs, fills, surveillance not modelled, price bands / volume caps / circuit locks / settlement lag not modelled. Listed as **not assessed** (each needs a data check outside this build): 2-decimal cash handling, retry-window re-pricing, names without dividends, Muhurat sessions, missing 2019 index days, the draft tax table across 2018/2024, universe holes, execution delay.
- `report --candidate ID` charts 11-24. Chart 11's "holdout shaded" and chart 24 are placeholders until phase 5 (the holdout stays locked and no holdout data can reach a report).
- The SPA test is Hansen's studentised statistic with a stationary bootstrap (mean block 20 days, 1,000 draws); calibration was checked on null data (5% level rejects 6.7% of 60 datasets).

## Phase 5 (holdout, promotion, shadow)
- `gate` now also registers the **holdout pass criterion** (`candidates/<id>/criterion.json`, hash in `gate.json`): post-tax CAGR above zero, drawdown within 1.5x the candidate's pre-holdout depth and the 30% cap, at least 15 fills a year, and not more than 2 pp below the live default. It detects catastrophic failure only (a 2-year Sharpe has a standard error of about 0.85). Evidence cannot be regenerated once the holdout is scored.
- `holdout --candidate ID` (exit 3 when refused or not passed): requires gate passed and a clean exploit audit, the criterion unchanged since the gate, no earlier holdout for this candidate, and the global `holdout.lock`. The backtest's marker (`hpo/data/holdout.marker`, `api.holdout_guard`) is taken before anything is simulated, so a crash still uses the look and is recorded (`holdout.json` status `error`); a second, different parameter set raises `HoldoutRead` (exit 3). The live default is also run over the holdout as a reference (not a selection). Nothing in a report before this point can contain holdout data; chart 24 draws the result once, after.
- `promote --candidate ID` writes `overlay.json` (changed keys only, dotted paths for `risk.json` / `analyst.json`), `rollback.json` (the old values; applying it restores the live config exactly, rehearsed in a test), `diff.md` (old/new with the register's class and note, frozen-class changes called out), and `dossier.json` / `.md`. It refuses unless gate, audit and holdout all passed. It never writes `app/config`; you apply the overlay by hand and bump `config_version`.
- The shadow limits are fixed in the dossier: 13 weekly rebalances, cumulative tracking gap within +-2 pp, and the shadow drawdown not past the backtest's 95th-percentile depth (computed from the candidate's pre-holdout returns). `shadow check --candidate ID [--nav CSV] [--since DATE]` compares the shadow portfolio's TWR index (default `app/data/risk/nav/nav_shadow.csv`) with the candidate replayed over the same days, writes `shadow.json` (shown in chart 24) and exits 3 when a rollback line is crossed. Both series are pre-tax. It tests fidelity, not edge.
- Not done: phase 6 (the annual re-optimisation runbook and its triggers). Until then, re-optimising more than once a year is a manual decision that the ledger records but does not block.

## Capital (Rs 4.5 lakh)
- The shipped capital is Rs 4.5 lakh (it was 1 lakh, then 2 lakh; at both the live `minNewOrderInr` 25,000 placed no order): `app/config/analyst.json` `capital.floatingCapitalInr` and `backtest/config/backtest.json` `capital.inr` (HPO has no capital key of its own: it simulates with the backtest's). The Risk Manager's real NAV comes from `app/config/cash_flows.csv` (an OPENING row and DEPOSIT rows), which is your data and is not edited by the repo.
- `doc/parameter_register.csv` and `hpo/schema/parameters.schema.json` were regenerated (the schema carries a hash of the register). A study started at another capital refuses to resume (the base configuration hash changed): start a new one.
- The TDD's "Rs 1 lakh" statements (D2, Stage 0 wording, the feasibility funnel caption) describe the capital it was written for. Constraint limits (fills, exposure, drawdown) were not re-derived for 2 lakh: calibrate them with `probe` and `study diagnose`.
- Why 4.5 lakh: `hpo.cli capital` solves the sizer's arithmetic gate for capital. One entry must reach the minimum order after the name cap (10% LargeCap), the bucket budget (weight / top_n: 0.5/8 = 6.25% of NAV in BEAR) and whole-share rounding (one share, Rs 2,000 assumed): Rs 2.7 lakh opens a LargeCap position in BULL or TREND, Rs 3.24 lakh in WEAK, Rs 4.32 lakh in BEAR. The one-line check (25,000 / 10%) says Rs 2.5 lakh and is too low. A drawdown-cut exposure cap (ladder) raises the bound again. The formula agrees with the real engine on the synthetic world (no entries below the bound, entries above it), and a test fails if the shipped capital falls under it.
- On the probes at Rs 2 lakh (before this change): the live sizing traded nothing; with a 3,000 minimum it made 3,150 fills at 28% average exposure, -2.7% CAGR and a 54.5% drawdown; with a 10,000 minimum 1,458 fills, 19% exposure, -0.55% CAGR and a 42% drawdown. Per-fold drawdowns never exceeded 24%, so the deep drawdown sits in the first five years (2008), which the folds do not measure.

## Review of studies s0, sA, sB, sC (Oct 2026)
- **sC stopped on a dead worker, not on the strategy.** Three trials failed with `BrokenProcessPool` and 3 of 50 is over the 5% share. A spawn pool never recovers from one dead worker, so the study could not continue. `EvalPool.restart` now replaces the executor once per breakage and `Study._run` runs each affected trial once more (test: `test_a_worker_that_dies_does_not_fail_the_trials...`). Why the worker died is not known (no log survives); suspect memory with 8 workers.
- **Nothing was feasible because the live default is not.** At Rs 4.5 lakh the default probe gives 0.3% full-span CAGR, 19.9% exposure and a 36% drawdown (breaks the exposure and drawdown limits). In sC 40 of 104 trials hit the -35% abort and 39 of 59 scored trials broke the -30% cap. The sampler had no feasible anchor, and 104 TPE trials over 93 dimensions is too few: `stages advise` says to stay on TPE (under 151 trials).
- **Exposure and return pull apart.** Probes at Rs 4.5 lakh: live (minNewOrderInr 25,000) 19.9% exposure, +0.3% CAGR, 36% drawdown; minNewOrderInr 5,000: 30.6%, -2.4%, 53%; 5,000 with the loosest ladder inside its bounds: 37.3%, -3.9%, 63%. Charges are 3-6% of NAV a year at 12-21x turnover because small orders pay a fixed Rs 23.6 DP charge per sale plus 10-25 bps slippage per side (about 1% a round trip at Rs 5,000). Lowering the minimum order opens positions but the strategy's gross edge does not cover the cost; the sC trials show the same (CAGR within +-2% for every minimum from 3,000 to 25,000).
- **The ladder starves entries when cut back.** The bucket budget is weight x NAV x ladder cap, and entries shrink to fit it. At Rs 4.5 lakh a LargeCap entry is 45,000 at the name cap, 8 of them need 360,000, so at the 75% cap (a 10% drawdown) each is about 21,000, under the live 25,000 minimum: no entry opens until the ladder releases. The ladder floor is measured from the all-time peak, so a strategy that stays underwater stays cut back. The "smallest capital" in the section above does not include this.
- **Not changed:** the live sizing minimums, ladder levels and the drawdown / exposure limits. They are risk decisions; the drawdown depth of 53-63% in the probes comes from the simulated owner restart (`ladder.autoRestart`) resetting the ladder peak, so a -30% cap on the full span cannot hold for a strategy with no net edge. A study that unfreezes the ladder needs `allow_unfreeze: ["group:ladder"]`.
- **Limits changed after this review (your decision):** `maxDrawdown` -30% -> -40%, `abortDrawdown` -35% -> -45% (it must not sit above the cap, or a trial between the two is aborted although it is feasible), `hvReference` depth 0.35 -> 0.45 (the hypervolume reference must lie beyond the feasible depths), and `minAvgExposure` 25% (already changed by you). The holdout criterion reads the cap from the same setting. Studies sA-sC used the old limits; their records are not comparable, so start a new study (`sD`).
- **Study sD (limits -40% / -45% / 25%), stopped by hand at 105 of 400 trials.** 93 scored, 28 feasible, 12 aborted on drawdown, 0 failed (a worker died at 23:58 on 7 Oct and the rebuilt pool re-ran its trials without a FAIL). Full-span CAGR over the scored trials: median -0.9%, 24 positive, 1 above 2%; the best (trial 75, +3.9%, 26% drawdown, 37% exposure, 3,248 fills, minNewOrderInr 13,000) has a worst fold of -11%, so it is not a candidate. Importance is spread thin (largest 0.07), `sensitivity` keeps 25 of 93 (`proposed_active.yaml`). Trial time rose from 450 s to about 1,500 s as TPE moved to high-fill configurations (correlation of seconds with fills 0.53); a run of 400 would take about 19 hours. The study resumes exactly with `study resume --name sD`.


## What HPO optimises, and what each study is for
**Optimised (93 `tunable` dimensions; the screen is `active: ["class:tunable"]`).** Everything is a key of `app/config/risk.json` or `analyst.json`, found through `doc/parameter_register.csv`:
- Signal (stage 1, 51): `selector` (momentum skip, minimum momentum, trend buffer, liquidity window and minimum ADV, the five bear-score weights, windows and confirm threshold) and `strategies` (per regime BULL / TREND / WEAK / BEAR: `top_n`, `lookback`, `stock_trend_ma`, a base value plus a per-bucket offset for MidCap and SmallCap).
- Stops, sizing, exposure (stage 2, 28 plus 9 frozen): `sizing` (risk per position, name caps, `minNewOrderInr`, `minAdjustmentInr` through a ratio, no-trade bands), `stops` (ATR period and multiplier, clamp low and width per bucket), `cooldown`, `ladder.reRisk` and `restartRungOffset`, `exposure.regimeCap` per regime, `liquidity` (ADV days, participation caps), `tax.deferral`.
- Regime and composition (stage 3, 8): `regime` (fast and slow SMA, momentum window and threshold, persistence weeks, unknown extra) and the bucket `composition` (the backtest copy follows it).
- Not searched (frozen unless a study lists `allow_unfreeze`): the 9 `risk-limit` keys (ladder levels, heat cap, cash buffer), costs, tax schedule, structural and design keys, and the capital.
- Judged on: post-tax CAGR (CVaR of the worst 30% of the walk-forward folds) and full-span max drawdown, with limits in `hpo/config/hpo.json` (drawdown -40%, 300 fills, exposure 25%, abort at -45%).

**Stages** (`stage:` in a study file; the search method, not a different parameter set, except stage 0):
| Stage | Meaning | Studies |
|---|---|---|
| 0 Feasibility | only the 6 stage-0 keys (risk per position, three name caps, minimum new order, minimum adjustment): can the account trade at all | `s0`: Sobol, 96 trials; interrupted at 11 (status.json still says running) |
| A Screen | all 93 tunable keys, to rank importance and decide what to freeze | `sA`: Sobol, 512 planned, interrupted at 44, 0 feasible. `sB`: TPE, 400 planned, interrupted at 56, 0 feasible. `sC`: TPE with the exposure floor 40% -> 25%; stopped at 104 by the dead-worker rule (3 `BrokenProcessPool` fails, since fixed). `sD`: TPE with drawdown cap -30% -> -40% and exposure 25%; stopped by hand at 105: 28 feasible, front of 4 |
| B Search | the 25 most important keys (`sD/proposed_active.yaml`), TPE in blocks | not run (`sD-next` is the proposed file) |
| C Refine | at most 25 keys, GP sampler | not run |
| D Polish | optional local robust polish of continuous keys (CatCMAwM) | not run (do not confuse with the study named `sD`, which is Stage A) |
Naming: `s0` and `sA`-`sD` are study names, not stages; four of them are Stage A re-runs because each earlier one found no feasible region (sA/sB: exposure floor 40% never met; sC: drawdown cap -30% never met at the live default's 36%).

## Applied configuration (sD trial 75, picked by Calmar from the 4-point front)
- Written by hand-free replacement of the 81 changed leaf values (the `hpo.cli promote` overlay format: 28 in `risk.json`, 53 in `analyst.json`) so the files keep their layout; the backtest reads them through `app/config`, and `backtest.json` `capital.composition` is set to the same 0.44 / 0.32 / 0.24. HPO takes its base from the same files, so a new study now starts from this point. `doc/parameter_register.csv` and `hpo/schema/parameters.schema.json` were regenerated.
- Result in the study (post-tax, 2008-2024, Rs 4.5 lakh): full-span CAGR +3.9%, drawdown 25.8%, average exposure 37%, 3,248 fills, Calmar 0.15; the study objective (CVaR of the worst folds) is -7.5%, with a worst fold of -11%. **This did not go through `gate`, `holdout` or `promote`**, no shadow period was run, and it is the best of about 28 feasible points of a 105-trial search over 93 dimensions: treat it as the best found, not as a demonstrated edge (see the honest-edge note above). Roll back with `git checkout app/config backtest/config/backtest.json`.
- Minimums changed with it: `minNewOrderInr` 13,000 (was 25,000), `minAdjustmentInr` 2,400. Smallest account at which this configuration opens a position (`hpo.cli capital`): Rs 1.07 lakh in BULL and TREND, Rs 1.7 lakh in BEAR, Rs 2.73 lakh in WEAK; every regime Rs 2.73 lakh (3 lakh rounded).

## Capital is configurable from Rs 1 lakh
- `backtest.json` `capital.inr` (the shipped Rs 4.5 lakh) and the CLI flag `backtest.run --single|--compare --capital INR` override it for one run; `hpo.json` `capital.inr` (null = use `backtest.json`) sets it for every HPO world (studies, probe, capital). All three refuse less than Rs 1,00,000 (`backtest/config.py` `MIN_CAPITAL_INR`). The live app's capital is the Risk Manager's NAV from `cash_flows.csv`; `analyst.json` `capital.floatingCapitalInr` stays your manual figure (0 or more).
- A smaller account trades only if the sizing allows it: below about Rs 1.07 lakh this configuration places no order, and between 1.07 and 2.73 lakh it skips the regimes listed above. The HPO result was found at Rs 4.5 lakh; for another capital re-run `capital` and a study (the cache keys include the capital).
